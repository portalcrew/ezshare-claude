# State ownership and persistence

The shared Claude credential belongs to the repository's account owner. Computer identity, conversation records,
workspace and history key belong to one authenticated GitHub member. The archive is bound to the repository and
member through AES-GCM associated data. Another member cannot open it with their own key.

## GitHub and browser state

| State | Reader | Writer and persistence |
| --- | --- | --- |
| Default branch and protection settings | Launcher and verified workflow execution | Repository administrators; determine which code receives credentials and personal keys. |
| Actions secret `EZSHARE_CLAUDE_TOKEN` | Chat workflow, then the unprivileged Claude/Morty processes through their explicit environment | Account-sharing flow writes the encrypted repository secret. It is separate from personal history. |
| Actions cache `ezshare-history-<actor-id>-run-<run-id>` | The next workflow's cache-restore step | Cache-save step writes the completed encrypted archive; earlier caches are immutable snapshots. |
| Encrypted mailbox Issue comments | Launcher and the matching verified runner | Both sides write authenticated ciphertext; comment authorship alone grants no authority. |
| Channel public-key artifact | Launcher, after verifying run ownership and attempt | The matching runner publishes it. Private channel keys are not published. |
| Launcher IndexedDB `ezshare-claude`, store `vault` | Launcher on the same origin | Launcher stores its non-extractable vault key and encrypted connection, pending-session and per-repository/member history slots. |
| Browser history key | Launcher; temporarily the authorized runner after encrypted handoff | Generated by the launcher and kept durably in its vault. It is never stored in GitHub Secrets or the history cache. |
| Morty browser access and E2E handoff | Morty on its own origin | Morty manages its own browser access. The launcher preserves the full private handoff fragment without logging it. |

Browser storage belongs to an origin. Moving the launcher to another origin, clearing site data or using another
browser profile does not carry its history key. Repository paths on the same Pages hostname are not separate origins.

## Files on the runner

`<home>` is the unprivileged agent home, normally `/home/ezshare-agent`. It has the same absolute path in each
fresh runner. Claude and Morty share `CLAUDE_CONFIG_DIR=<home>/.claude` and work in `<home>/workspace`.

| File or directory | Reader / writer | Archive treatment |
| --- | --- | --- |
| `<home>/.claude/projects/<encoded-workspace>/<session-id>.jsonl` | Claude Code and Morty's Claude adapter read and write native transcripts | Included. The selected file must exist and be nonempty before its ID is handed to Morty. |
| `<home>/.claude` settings and `<home>/.claude.json` | Claude and its adapter | Included, except `.claude/.credentials.json`. |
| `<home>/workspace` and `<home>/.config` | The member's agent tools | Included as personal workspace and configuration. |
| `<home>/morty/config.json` | Morty setup reads and updates identity and setup state | Included, encrypted with the member's history key. |
| `<home>/morty/computer/pairing.json` and encryption-access files | Morty setup and runtime | Included. These credentials belong to the personal Computer, not to the team's Claude account. |
| `<home>/morty/computer/sessions` | Morty runtime reads and writes its session records and event data | Included, including needed SQLite sidecars. These are Morty's existing local files; ezshare adds no database service. |
| Morty daemon PID/lock files, `*.lock.sqlite*`, and Computer logs | Morty processes | Excluded: process coordination and logs must not travel to a new VM. |
| `.cache`, `.npm`, `node_modules`, `.claude/.credentials.json` | Tools | Excluded. |
| Runner-temp `ezshare-history/history.bin` | Workflow step decrypts/restores, then encrypts/replaces; cache steps transfer ciphertext | Persistent cache payload. Version 1 manifest holds the selected Claude session ID. |
| Runner-temp plaintext/partial archive files | Workflow step only | Private temporary files; removed on completion or failure. Plaintext is unpacked only after authentication succeeds. |

The workflow step temporarily holds the history key to decrypt and encrypt the archive. Claude and Morty receive
only their required environment, not the step's GitHub token or channel private key. Public diagnostics contain
stages and allowlisted error codes, not tokens, private links or message contents.

## Session transition and recovery

The browser hands over its personal history key before the runner starts an Agent or Computer. If it does not do
so within the bounded startup wait, the run fails with `history_key_missing`; it does not silently create an
unsaved Computer. Keep the launcher open until ready. Older launchers may show their generic completed-run failure
for that new code, but the runner still fails closed.

On a readable archive, restore the personal files before Morty setup. Morty then reuses the saved Computer identity
and session/event state, while Claude continues the selected native session. After normal stop, encrypt the home
and save a new cache snapshot. A forced cancellation or VM failure before the save completes can lose changes
since the last completed snapshot.

Older archives excluded the entire Morty directory. Their missing Computer credentials cannot be reconstructed:
the first upgraded run creates a Computer once, and later saved/restored runs retain it. Existing Claude native
transcripts remain available. This does not promise recovery of Morty UI events that were never archived.

An unreadable archive is not overwritten automatically. Explicit history replacement starts fresh personal state,
including a new Computer. An old Morty tab can still remember an offline identity: enter through the launcher's
current private link after migration. Losing the browser history key has no server-side recovery or export flow.
